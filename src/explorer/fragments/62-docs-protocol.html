CoinCync Protocol Specification

This document describes the technical specification of the CoinCync protocol.

Overview

CoinCync is a privacy-focused cryptocurrency with:

  • Mandatory transaction privacy
  • Auditable supply via Pedersen commitments
  • RandomX Proof of Work — CPU-only, ASIC-resistant
  • Forward-secret view keys
  • Confidential assets
  • Encrypted P2P and RPC communication

Cryptographic Primitives

Elliptic Curve

CoinCync uses Curve25519 (Ristretto group):

  • Generator point: Standard Ristretto basepoint
  • All points are validated before use
  • Identity point rejected in key images

Hash Functions

PurposeAlgorithm

Address checksumBLAKE3 (first 4 bytes)

Privacy Features

Ring Signatures (CLSAG)

Each input uses a ring signature to hide the true sender:

  • Ring size: 11 (years 0-2), 16 (years 2-5), 21 (years 5+)
  • Key images prevent double-spending
  • CLSAG provides logarithmic signature size
  • Testnet: ring size 2 allowed on young chains (height < 10,000)

Stealth Addresses

Each output uses a unique one-time address derived from:

  • Transaction secret (random)
  • Recipient view public key
  • Recipient spend public key

Coinbase outputs use ECDH-derived stealth addresses unique per block.

Subaddresses

Unlinkable receive addresses derived from a single wallet:

  • Derivation: m = H(view_secret || account || index), subaddr_spend = m*G + spend_public
  • Cannot be linked to the primary address by outside observers
  • Each subaddress can independently receive and be scanned

Pedersen Commitments

Amounts are hidden using Pedersen commitments:

  • C = v * G + r * H
  • v = amount (hidden)
  • r = blinding factor (random)
  • G, H = generator points

Bulletproofs

Range proofs ensure amounts are valid (0 to 2^64 - 1):

  • Aggregated proofs for multiple outputs
  • Logarithmic proof size
  • No trusted setup required
  • Padded to power-of-2 aggregation count

Dandelion++

Transaction propagation uses Dandelion++:

  • Stem phase: 2-7 hops to single peer
  • Fluff phase: Broadcast to all peers
  • Protects originator IP address

Confidential Assets

Based on the Poelstra et al. 2017 scheme:

Asset Model

  • Each asset has a unique 32-byte AssetId
  • Assets are created via issuance transactions with Schnorr-signed policies
  • All asset transfers use the same privacy primitives as native CYNC

Asset Commitments

Each output commits to its asset type:

  • asset_generator = H_asset(asset_id) (asset-specific generator point)
  • asset_commitment = asset_generator + r_asset * H (blinded)
  • Hides which asset type is being transferred

Asset Surjection Proofs

A 1-of-n ring signature (Borromean convention) proves the output's asset type is one of the input asset types without revealing which:

  • Proves no new asset types created from nothing
  • Ring covers all input asset types

Asset Audit

Issuers can decrypt encrypted_asset_audit fields to verify their asset's circulation using the issuer's view key.

Encrypted Communication

P2P Encryption (Noise_XX)

All node-to-node communication uses the Noise_XX handshake pattern:

-> e                          (initiator sends ephemeral pubkey)
<- e, ee, s, es              (responder sends ephemeral + static)
-> s, se                      (initiator sends static)

Primitives:

ComponentAlgorithm
DHX25519 (x25519-dalek)
AEADChaCha20-Poly1305
Hash/KDFBLAKE3-based HKDF

Properties:

  • Forward secrecy via ephemeral X25519 keys per session
  • Mutual authentication via static keys
  • Node identity persisted at {data_dir}/node_key

Wire format (post-handshake):

[2 bytes LE: ciphertext_len] [encrypted_payload] [16-byte Poly1305 tag]

Backward compatibility:

  • 1-byte proposal: 0x01 = "I want Noise"
  • Responder replies 0x01 (accept) or 0x00 (reject)
  • If encryption.required = false and peer rejects, falls back to plaintext

RPC Encryption (TLS)

The JSON-RPC server uses TLS by default:

  • Auto-generated self-signed ECDSA P-256 certificate
  • Certificate stored at {data_dir}/rpc_cert.pem and rpc_key.pem
  • Certificate fingerprint logged at startup for client pinning
  • Optional mutual TLS with client certificates
  • Disable with --no-rpc-tls for local development

Consensus: VDF-Anchored Proof of Work

Mining Steps

1. Sequential Anchor (VDF): 4 million iterations of sequential hashing (cannot be parallelized)

2. Memory-Hard Mix: Blake3 mixing with the anchor output

3. PoW: RandomX proof of work (CPU-only, ASIC-resistant)

4. Nonce Grinding: Standard Proof of Work — find a nonce that meets the difficulty target (parallelizable)

5. Decay Window: Solution must be found within 8-15 seconds

PoW Algorithms

IndexAlgorithmType
0RandomXCPU-friendly, 2GB dataset
0RandomXMemory-hard, 256MB cache, CPU-only

Difficulty Adjustment

  • Dual-Anchor ASERT algorithm
  • Short window: 20 blocks (70% weight)
  • Long window: 500 blocks (30% weight)
  • Half-life: 60 seconds

Address Format

Standard address format:

  • Prefix: CYNC (mainnet) or tCYNC (testnet)
  • Encoding: Base58
  • Components: version, type, spend key, view key, checksum

Key Epochs

View keys rotate every 50,000 blocks (approximately 3.5 days):

  • Provides forward secrecy
  • Limits view key exposure window
  • Grace period of 2 epochs for transition

Transaction Validation

Required Checks

1. Version is 1

2. Size between 500 and 500,000 bytes

3. Input count 0-128

4. Output count 1-16

5. Ring size matches network requirement

6. No duplicate key images

7. Ring signatures verify

8. Range proofs verify

9. Balance equation holds

10. Key images not spent globally

11. Asset surjection proofs verify (if asset outputs present)

Network Protocol

Connection Limits

  • Maximum peers: 128
  • Minimum for sync: 3
  • Per-IP limit: 1
  • Connection timeout: 30 seconds
  • Noise handshake timeout: 10 seconds

Message Size Limits

  • Maximum message: 16 MB
  • Maximum block: 2 MB
  • Maximum transaction: 500 KB

Peer Discovery

  • DNS seed resolution (with 5s timeout)
  • Hardcoded seed node addresses
  • Peer exchange (addr messages)
  • --seed-node CLI override
