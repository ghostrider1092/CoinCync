CoinCync Privacy Features

This document explains how privacy works in CoinCync.

Ring Signatures

How They Work

When you send CYNC, your transaction input is mixed with decoys:

1. Your real input is selected

2. 10 additional decoy inputs are selected from the blockchain

3. A ring signature proves one of the 11 is real, without revealing which

4. An observer cannot determine which input is yours

Ring Size

Ring size increases over time for better privacy:

PeriodRing SizeAnonymity Set
Year 0-2111 in 11
Year 2-5161 in 16
Year 5+211 in 21

On young testnet chains (height < 10,000), a minimum ring size of 2 is allowed to bootstrap the network. Privacy improves as more outputs become available.

Key Images

Each output can only be spent once. Key images ensure this:

  • Generated from the output and your secret key
  • Unique to each output
  • Reveals nothing about the output itself
  • Stored on blockchain to prevent double-spending

Decoy Selection

CoinCync uses intelligent decoy selection:

  • Based on realistic spending patterns
  • Age-weighted distribution (gamma distribution)
  • Minimum and maximum age limits
  • Deduplication by public key before ring construction
  • Prevents statistical analysis attacks

Stealth Addresses

One-Time Address Derivation

Every transaction output goes to a unique one-time address:

1. Sender generates a random transaction secret

2. Sender computes shared secret with recipient view key

3. One-time address is derived from shared secret

4. Only recipient can recognize and spend the output

Benefits

  • No address reuse
  • Cannot link transactions to an address
  • Recipient address never appears on blockchain
  • Even sender cannot identify recipient later

Coinbase Stealth Addresses

Mining rewards use ECDH-derived stealth addresses that are unique per block, preventing stealth index collisions on the UTXO set.

View Tags

For efficiency, each output includes a 1-byte view tag:

  • Wallet can quickly filter outputs
  • 255/256 non-matching outputs rejected instantly
  • Full computation only for potential matches

Subaddresses

Subaddress Derivation

Subaddresses are unlinkable receive addresses derived from a single wallet:

1. Derivation: m = H(view_secret || account || index)

2. Subaddress spend key: m*G + spend_public

3. Each subaddress has its own view key component

Privacy Benefits

  • Cannot be linked to your primary address by outside observers
  • Cannot be linked to each other without your private keys
  • Give each sender a unique address for payment tracking
  • Separate business and personal payments

Management

cync-wallet --wallet mywallet --password <pass> --network testnet subaddress new
cync-wallet --wallet mywallet --password <pass> --network testnet subaddress list
cync-wallet --wallet mywallet --password <pass> --network testnet subaddress label 0 "Donations"

Pedersen Commitments

Commitment Scheme

Transaction amounts are hidden using commitments:

  • Commitment = amount * G + blinding * H
  • G and H are generator points
  • Blinding factor is random
  • Amount is hidden but committed

Homomorphic Property

Commitments can be added and subtracted:

  • sum(input_commitments) = sum(output_commitments) + fee_commitment
  • Verifiers check equation without knowing amounts
  • Proves no coins created from nothing

Auditable Supply

This is what makes CoinCync unique:

  • Every transaction proves balance
  • Chain of commitments proves total supply
  • Anyone can verify no inflation occurred
  • Privacy maintained for individual amounts

Bulletproofs

What They Prove

Range proofs ensure amounts are valid:

  • Amount is between 0 and 2^64 - 1
  • No negative amounts (no coin creation)
  • No overflow attacks

Efficiency

Bulletproofs are logarithmic in size:

  • Single output: ~672 bytes
  • Multiple outputs: Aggregated, sublinear growth
  • Padded to power-of-2 aggregation count for batch verification

Zero-Knowledge

Proofs reveal nothing except:

  • Amount is in valid range
  • Same blinding factor as commitment

Dandelion++

Network Privacy

Transaction propagation protects your IP:

1. Stem Phase: Transaction sent to single peer

2. Each peer either:

  • Continues stem (90% chance)
  • Fluffs to network (10% chance)

3. After 2-7 hops or timeout, broadcast begins

4. Fluff Phase: Normal broadcast to all peers

Privacy Guarantees

  • Observers cannot determine transaction origin
  • Even network-level adversaries face uncertainty
  • Probabilistic protection against timing analysis

Parameters

ParameterValue
Minimum stem hops2
Maximum stem hops7
Fluff probability10%
Stem timeout60 seconds

Noise Protocol (Encrypted P2P)

How It Works

All node-to-node communication is encrypted using the Noise_XX handshake pattern:

1. Initiator sends ephemeral X25519 public key

2. Responder sends ephemeral + static keys (encrypted)

3. Initiator sends static key (encrypted)

4. All subsequent traffic uses ChaCha20-Poly1305 AEAD

Noise Privacy Benefits

  • Traffic analysis resistance: P2P messages are encrypted and indistinguishable
  • Forward secrecy: Ephemeral keys per session; past traffic safe even if static key leaks
  • Mutual authentication: Both peers prove identity via static keys
  • ISP blindness: Network observers cannot identify CoinCync protocol traffic

Node Identity

Each node has a persistent X25519 keypair stored at {data_dir}/node_key:

  • Generated automatically on first run
  • Used for authentication during Noise handshake
  • Public key serves as a stable node identifier

Noise Configuration

# Require all peers to use encryption (reject plaintext)
coincync-node --require-encryption --data-dir ./data --network testnet

# Default: prefer encryption, fall back to plaintext if peer doesn't support it

Tor Support (SOCKS5 Proxy)

Proxy Routing

CoinCync can route all P2P traffic through a SOCKS5 proxy (typically Tor):

  • Hides your node's real IP address from peers
  • Supports .onion hidden service connections
  • Tor is NOT bundled — install separately

Tor Configuration

# Route through Tor
coincync-node --proxy --proxy-address 127.0.0.1 --proxy-port 9050 \
  --data-dir ./data --network testnet

# Only connect to .onion peers
coincync-node --proxy --onion-only --data-dir ./data --network testnet

Combined with Noise

Noise encryption runs on top of the proxied TCP connection. The proxy sees only encrypted traffic, adding defense in depth even if the proxy is compromised.

TLS for RPC

RPC Encryption

The JSON-RPC server uses TLS by default:

  • Auto-generated self-signed ECDSA P-256 certificate
  • Protects wallet commands and credentials in transit
  • Certificate fingerprint logged at startup for pinning

Wallet Connection

# Default: TLS enabled (accepts self-signed certs)
cync-wallet --wallet mywallet --password <pass> --daemon 127.0.0.1:28081 sync

# Disable TLS for local development
cync-wallet --wallet mywallet --password <pass> --no-tls --daemon 127.0.0.1:28081 sync

# Pin server certificate
cync-wallet --wallet mywallet --password <pass> \
  --tls-fingerprint <sha256hex> --daemon 127.0.0.1:28081 sync

Forward-Secret View Keys

Key Epochs

View keys change every 50,000 blocks (approximately 3.5 days):

  • Current epoch key sees current transactions
  • Old keys cannot see new transactions
  • Limits exposure if view key is shared

Privacy Benefit

If your view key is compromised:

  • Attacker sees only that epoch's transactions
  • Future transactions remain private
  • Past epochs may also be protected

Grace Period

Two-epoch grace period for:

  • Wallet synchronization
  • Incoming transactions during transition
  • Smooth key rotation

Transaction Privacy Best Practices

Do

  • Wait for confirmations before spending received funds
  • Use subaddresses for each sender/payment purpose
  • Keep wallet software updated
  • Use Tor or VPN for additional network privacy
  • Enable Noise encryption (default)
  • Use TLS when connecting to remote nodes

Avoid

  • Spending immediately after receiving
  • Reusing addresses
  • Sharing view keys unnecessarily
  • Connecting to untrusted nodes
  • Disabling encryption without good reason

What Ring Signatures Do Not Hide

  • Transaction occurred
  • Approximate transaction time
  • Number of inputs and outputs
  • That one ring member is real

Metadata

CoinCync protects transaction contents but:

  • Blockchain is public
  • Block timestamps are public
  • Transaction size is visible
  • Network monitoring may reveal IP without Tor

  • Business auditing
  • Proving payment receipt

Technical Details

Cryptographic Foundations

  • Curve: Curve25519 (Ristretto)
  • Ring Signature: CLSAG
  • Commitment: Pedersen
  • Range Proof: Bulletproofs
  • Hash: BLAKE3, SHA3-256
  • P2P Encryption: Noise_XX (X25519 + ChaCha20-Poly1305)
  • RPC Encryption: TLS 1.3 (ECDSA P-256)

Security Assumptions

  • Discrete logarithm problem is hard
  • Hash functions are collision-resistant
  • Random number generation is secure
  • Implementation is correct
