# v1.0.11 Architecture Review — Stability Path to Mainnet

**Author:** Sebastian (project lead)
**Date:** 2026-06-03
**Scope:** Root-cause analysis of the cluster of stability bugs surfaced
2026-06-01 → 06-03 during community testing. Concrete remediation plan
to actually fix the underlying architecture before mainnet, rather than
shipping more band-aids.

**Reading time:** ~15 minutes. Action items ranked at bottom.

---

## TL;DR

CoinCync has **5 architectural patterns** that compound into the
stability bugs we keep finding:

1. `parking_lot::RwLock<BlockchainInner>` used from `async` contexts
2. `Blockchain::add_block` holds the read lock across CPU-bound validation
3. RPC handlers all run on the small tokio worker pool
4. No headers-first sync (orphan-fetch cascade)
5. Implicit task ownership for per-peer connection tasks

Of these, **#1 and #2 are the lever that fixes the most symptoms** —
they're the root cause of worker starvation, RPC silent hangs, and
the "everything stalls when sync is busy" pattern. The other three
are real but lower-leverage.

Effort to fix #1 + #2 properly: **~2 weeks of focused work**.
Effort to fix all five: **~6 weeks**.

The current 2026-10-01 mainnet date is achievable for #1 + #2 ONLY
if engineering starts in June. The headers-first sync rewrite (#4)
realistically slips mainnet to Q1 2027 unless we descope it.

## Finding 1 — `parking_lot::RwLock` on chain state in async context

**Severity:** Critical. Root cause of every "RPC silent hangs"
incident this week.

**Where:** [`src/chain.rs:7`](../src/chain.rs) `use parking_lot::RwLock;`,
applied at [`src/chain.rs:354`](../src/chain.rs) as
`inner: RwLock::new(BlockchainInner { ... })`.

**Why it's wrong:**

`parking_lot::RwLock` is a sync (blocking) lock. `.read()` and
`.write()` block the calling OS thread. When called from an `async`
task, this blocks the tokio worker thread the task is running on
(not just the task — the whole worker).

Tokio defaults to `num_cpus` worker threads (a 2-vCPU Vultr box gets
2). We hardcoded `worker_threads = 8` in
[`src/bin/node.rs:141`](../src/bin/node.rs) but that's a thin shim
over the real problem: every chain access is a potential blocker.

**Concrete failure mode observed 2026-06-03:**

1. Sync engine holds `inner.write()` during `add_block` validation
   (~500ms per block including RandomX hash check).
2. RPC handlers call `state.chain.tip()` → `inner.read()` → blocked
   waiting for the writer.
3. After 8 RPC requests block on chain reads, the entire tokio runtime
   is stalled. New requests can't even be scheduled.
4. Outside observer: "RPC silently stopped responding."

We band-aided this in rc3 by:
- Bumping `worker_threads` 4 → 8
- Converting 3 hottest RPC handlers to `register_blocking_method`
  (`get_info`, `get_peer_info`, `get_blockchain_info`)

But 36 other RPC handlers are still on the tokio workers and will
hit the same pathology under load.

**Real fix — two options:**

### Option 1.A — `tokio::sync::RwLock` replacement

Change `parking_lot::RwLock<BlockchainInner>` →
`tokio::sync::RwLock<BlockchainInner>`. `read().await` and
`write().await` are non-blocking — they yield the worker thread
while waiting.

**Cost:** Every consumer of `chain.inner` has to `.await` the lock
acquisition. Hundreds of call sites. Some are inside sync (non-async)
contexts and need a `block_on` wrapper OR refactoring to async.

**Benefit:** Fixes the architectural mismatch at its source. No more
worker-thread-blocking on chain reads, ever.

**Effort:** ~1 week to make the mechanical change + audit every call
site. Plus ~3 days of testing because the lock semantics differ
subtly (tokio's RwLock is write-preferring, parking_lot is reader-
fair by default).

### Option 1.B — Spawn-blocking pattern uniformly

Keep `parking_lot::RwLock` but require every async caller to wrap
chain access in `tokio::task::spawn_blocking`. The blocking thread
pool (default 512 threads) absorbs the lock-held duration without
starving workers.

**Cost:** Every async chain access is `let result = task::spawn_blocking(|| chain.tip()).await?`.
Verbose, easy to forget, no compile-time enforcement.

**Benefit:** Smaller, more local change.

**Effort:** ~3 days to convert all 36 remaining RPC handlers +
audit non-RPC async paths.

**Recommendation:** **Option 1.A** is the right architectural fix.
Option 1.B is what we've been doing piecemeal and it doesn't scale —
every new feature creates another opportunity to forget the
spawn_blocking wrapper. Bite the bullet, do the real refactor for
v1.0.11.

## Finding 2 — `add_block` holds the read lock across validation

**Severity:** High. Independent of Finding 1 — even with
`tokio::sync::RwLock`, holding any lock for 500ms+ during PoW
verification creates pathological contention.

**Where:** [`src/chain.rs:1221`](../src/chain.rs) `pub fn add_block`,
specifically the validation block at lines 1312-1334:

```rust
{
    let inner = self.inner.read();          // ← lock acquired
    let validation = crate::consensus::validate_block_with_checkpoint_for_network(
        &block,
        parent.as_ref(),
        &inner.utxos,                       // ← validation needs utxos by ref
        cp,
        self.network,
    ).map_err(|e| ...)?;
    if !validation.valid { ... }
}                                            // ← lock released
```

`validate_block_with_checkpoint_for_network` does:
- RandomX PoW hash verification (~200-500ms)
- CLSAG ring signature verification (~10-30ms per input)
- Bulletproof range proof verification (~50-100ms per output)
- Merkle root reconstruction
- Coinbase reward check

For a typical block, total = 300-800ms. **The read lock is held
the entire time.** During that window, ANY writer blocks, and any
reader queued after the writer also blocks (FIFO fairness).

**Concrete failure mode:**

Two concurrent `add_block` calls (one for the main chain, one for
a fork attempt) serialize at the write step. But the READ lock
during validation also blocks the OTHER add_block from acquiring
its own read. Under heavy fork-resolution load, add_block latency
compounds: 500ms per block becomes 2s, 5s, 10s as the queue grows.

The "race detected" band-aid at line 1479 (`Tip changed during
block processing`) papers over this: when the tip changed during
our long lock window, the block is reclassified as a fork. That
works mechanically but creates wasted CPU (validated a block
that's now on the wrong chain).

**Real fix:**

Restructure `add_block` to:

1. Acquire read lock briefly, **snapshot** what's needed for validation
   (utxos snapshot — make `UtxoSet` cheaply cloneable via `Arc`-of-
   inner pattern), drop lock.
2. Do CPU-bound validation against the snapshot (no lock held).
3. Acquire write lock briefly.
4. Re-verify the snapshot is still current (TOCTOU check — same as
   today's "race detected" check but cleaner).
5. Apply mutations.
6. Drop lock.

**Cost:** Refactor `add_block` (~150 lines of code). Make `UtxoSet`
snapshottable — likely add `Arc<UtxoSetInner>` or similar.

**Benefit:** Lock contention drops from 500ms per block to <5ms per
block. Worker starvation pathology disappears even without Finding 1.

**Effort:** ~3-5 days including UtxoSet snapshot work + testing
under fork-resolution stress.

## Finding 3 — RPC handlers vulnerable to worker starvation

**Severity:** High. Same root cause as Finding 1; partial fix
shipped in rc3.

**Where:** [`src/rpc/server.rs`](../src/rpc/server.rs) — 39 total
RPC method registrations. As of `6a3667f`, only 3 use
`register_blocking_method`:
- `get_info` (line 438)
- `get_peer_info` (line 559)
- `get_blockchain_info` (line 630)

**The other 36** still use `register_method`, which runs the handler
on a tokio worker. Most of them call `state.chain.<something>()`,
which acquires the parking_lot read lock, which blocks the worker.

**Real fix:**

Two layers:

1. **Short-term:** Bulk-convert the 33 chain-touching handlers to
   `register_blocking_method`. Three handlers genuinely have `.await`
   inside (need to stay async — most likely admission/relay paths
   that touch the mempool which is async-safe).

2. **Long-term:** When Finding 1 is fixed (tokio::sync::RwLock),
   handlers can stay async and the question becomes moot. But the
   short-term fix is worth doing anyway because it ships in 1-2 hours
   and provides immediate protection.

**Effort:** 1-2 hours for the bulk conversion + verify each closure
doesn't have `.await`. Mostly mechanical.

## Finding 4 — No headers-first sync; orphan-fetch cascade is the symptom

**Severity:** High. Cause of every "node stuck for hours" incident
observed this session.

**Where:** [`src/network/sync.rs`](../src/network/sync.rs) `ChainSync`
state machine + [`src/network/node.rs:1213+`](../src/network/node.rs)
sync driver loop.

**Current architecture:** Reactive block-by-block via `inv` broadcasts.
When a peer announces a new block via `inv`, we request that block.
If its parent is missing, mark orphan + fetch parent. Cascading
backwards.

**Failure mode:** When local tip is N blocks behind a peer's tip,
peers broadcast their tip blocks via `inv`. We orphan all of them
because we're missing the intermediate chain. We try to fetch the
parents, but those parents are also broadcast-as-tip blocks → also
orphan. The chain never fills in.

Observed on `coincync-lon` 2026-06-02: stuck at h=14994 for 20+ hours
with 4 connected peers continuously sending GetHeaders that never
advanced.

**Standard fix (Bitcoin since 2014, Ethereum, Monero):** Headers-first
sync.

1. Download all headers from the peer with the highest cumulative
   work, in order.
2. Verify the header chain (PoW per header, parent linkage, difficulty
   transitions).
3. Once headers are validated, fetch bodies (block data) for the
   header chain in parallel, in order.
4. Apply bodies as they arrive.

This eliminates the orphan-fetch cascade entirely because we always
know what blocks to fetch (the headers tell us).

**Cost:** Significant rewrite of `ChainSync` state machine + sync
driver loop. New protocol messages (`GetHeaders` already exists;
need a real `Headers` response handler that maintains the header
chain). Block-body parallel fetch coordinator.

**Effort:** 4-6 weeks. The right v1.0.11 work.

**Calendar risk:** This is what would push mainnet to Q1 2027 if
not started by mid-June. Worth slipping the date for; without it,
mainnet operators will hit the same stall pattern under realistic
network conditions.

## Finding 5 — `ChainSync` requires write lock for any state read

**Severity:** Medium. Compounds Finding 1.

**Where:** [`src/network/sync.rs:57`](../src/network/sync.rs) `pub
struct ChainSync` — all internal state is plain `HashMap`/`HashSet`/`Vec`.
Methods like `update_peer_height_for`, `set_local_tip`, `queue_headers`
all take `&mut self`.

**Why it matters:** The sync state is wrapped in
`Arc<RwLock<ChainSync>>` in `node.rs`. Every state mutation needs
`.write().await` (or `.write()` if parking_lot). The diagnostic
RPC `get_peer_info` we added needs to read `peer_heights` — that
requires either:
- A read-only accessor that takes `&self` (cheap if we add it)
- Or `.write().await` (write lock) just to read

Right now we have a mix. Should be uniformly `&self` for reads,
`&mut self` only for genuine mutations.

**Real fix:** Audit `ChainSync` impl, split read-only methods to
`&self`, mutators to `&mut self`. Use interior mutability (DashMap
for `peer_heights`, atomics for counters) where contention is
high.

**Effort:** 1 week.

## Finding 6 — Peer connection tasks have implicit ownership

**Severity:** Medium. Cause of the eclipse-defense slot leak we
just fixed (`84f40ce`).

**Where:** [`src/network/node.rs`](../src/network/node.rs) connector
loop spawns `handle_connection` as `tokio::spawn`. The task owns:

- A clone of the `peers: Arc<DashMap<PeerId, PeerInfo>>` map
- A clone of `senders: Arc<DashMap<PeerId, mpsc::Sender<...>>>`
- An `Option<Arc<OutboundSubnetSlot>>` (for outbound dials)
- Various other Arc clones for chain/scorer/event broadcaster

When the task exits, it manually cleans up via
`peers.remove(&peer_id); senders.remove(&peer_id);`. The eclipse
slot is supposed to drop via Arc semantics when the PeerInfo entry
drops.

**The leak we just fixed** was a logic bug in the cleanup check
(should_remove evaluated wrong because `rx` was still in scope).
But the underlying pattern — manual cleanup of multiple maps + an
implicit Arc lifetime — is fragile. Any future change that adds
another resource to PeerInfo, or another map keyed by PeerId, is
another potential leak.

**Real fix:** Wrap PeerInfo + sender + slot in a `PeerHandle` struct
with a `Drop` impl that handles all cleanup. The connection task
owns one `PeerHandle`; when the task exits, Drop runs, cleanup is
automatic.

**Effort:** 1 week. Touches every peer-touching path.
