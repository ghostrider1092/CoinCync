## What got fixed

### Chain partition recovery (June 22-26)

The chain stalled at h=4170 on June 22 03:52 UTC due to an orphan-flood scoring incident. The fleet's view of the chain stuck for 18+ hours undetected. We:

1. **Diagnosed** the orphan-flood ban + identified the broken `--addnode` lists wasting outbound slots
2. **Recovered** via chaindata-tarball transfer (miner → seeds) — proven recovery pattern, ~10s downtime
3. **Fixed at root** in Layer 1 (PR #105): excluded the nginx-only `api` host from `--addnode` lists across all fleet nodes. The script `scripts/sync-fleet-config.sh` rolls this out staggered.

### Recurring miner-stall pattern (resolved)

The miner's local node was hitting a state where it briefly thought it was "not synced" and the rig sync-gate (correctly) refused to mine. Operator-driven recovery took 5-10 min but the stall went undetected for hours. **Now self-healed:**

- `scripts/miner-stall-watchdog.sh` — cron on miner box, runs every 5 min, restarts node + rig if no block accepted in 15+ min
- Anti-restart-loop guard: won't restart again within 10 min of last restart
- Already auto-recovered one stall (2026-06-26 22:55 UTC) — operator wasn't involved

### Stale peer cache (Layer 2 code fix)

Today's deep diagnosis revealed dead IPs (from destroyed fleet boxes) were sitting in the in-memory peer address book forever, getting re-gossiped between fleet members. Each dead IP burned an outbound dial slot via the eclipse-defense subnet counter.

**Code fix (this commit):** added peer-aging to `AddressManager`. After 5 consecutive failed dial attempts with no intervening success, the address is purged from the in-memory pool. Re-add via gossip is allowed (could be a host returning from maintenance) — fresh failure count starts.

### CI hardening

- **PR #103:** disabled `cargo-audit` yank checks (yanks aren't vulnerabilities and the Zcash team yanked all halo2_gadgets <0.5 overnight). RUSTSEC vulnerability gate stays strict.
- **PR #103:** bumped `quinn-proto` 0.11.14 → 0.11.15 for RUSTSEC-2026-0185 (high-severity remote memory exhaustion vuln).

### Per-release ledger (v1.0.11.5 → v1.0.12-rc1)

The v1.0.11 line shipped three back-to-back hardening releases (11.5 + 11.6 + 11.7, bundled into one published binary on 2026-06-20) followed by the v1.0.12 fork RC on 2026-06-26.

#### v1.0.11.5-testnet — broadcast stall fix
Closes the recurring ~640-second stall pattern (11 stalls in 13 hours on v1.0.11.4 binaries). Stale peer-height claims were pinning `best_known_height` above local, blocking the broadcast path indefinitely. Fix prunes peer-height entries the moment local advances past them — mirrors Monero's `cryptonote_protocol_handler` per-peer-remaining-work-collapse semantics.

#### v1.0.11.6-testnet — sync state-machine refactor
Wholesale `src/network/sync.rs` rewrite (+634/-111). Closes V1/V2/V4/I8/I10 violations from the sync state-machine audit:
- **V1**: `best_known_height` re-derived from `max(local, max(peers))` on every mutation — can now SHRINK when peers leave (Bitcoin Core `pindexBestHeader` pattern)
- **V2**: stale peer-height pruning applied in both `set_local_tip` AND `update_peer_height_for`
- **V4**: `downloading` / `download_timestamps` / `pending_requests` atomically synced via unified `record_request` (Bitcoin Core `mapBlocksInFlight`)
- **I8**: `downloading ≡ download_timestamps`, `pending_requests ⊆ downloading` — invariant enforced at every requeue/recover path
- **I10**: `Synced` state tolerates ≤16 in-flight blocks for InvBlock tip-catch-up (Bitcoin Core `IsInitialBlockDownload` carve-out)

Tests: 10 sync unit tests + 2,048-case proptest harness across 12 SyncEvent variants. 646/646 lib tests pass.

#### v1.0.11.7-testnet — silent-hang hardening trio
Targets the silent-process-hang class observed 2026-06-19 (3 of 5 fleet nodes had their maintenance loop die silently while systemd reported `active` for 17 hours):
- **C1** — Maintenance task supervisor (`JoinHandle` + sibling watcher → `CRITICAL` log on any termination); zebrad actor-model pattern
- **C2** — 30-second heartbeat line (`INFO node::heartbeat maintenance tick=N peers=M outbound=K`); external watchdogs detect freezes within ~60s instead of 17 hours
- **C2b** — `biased;` `select!` in maintenance so `ping_interval` (PEER_TIMEOUT=300s) is never starved by the higher-frequency cleanup loop
- **C3** — `shadow_evict_invalid` moved to `spawn_blocking` (Bitcoin Core `MaybeUpdateMempoolForReorg` pattern)

SHA-256: `26916e5d18daffcfa73ad52a01b929a61b300d7785cb9b514a4f83dcaef08d94`

#### v1.0.12-rc1 — testnet hard fork release candidate
**Activation: testnet h=13_000 (~2026-07-01).** CIP-007 Mode A (static-height flag day, no BIP-9 signaling window). Five consensus tightenings, all dormant on `main` since PR #68:

1. `encrypted_amount` tightened to exactly 8 bytes
2. Per-output size caps enforced at block-validation level
3. Duplicate stealth addresses rejected within a tx
4. Cross-tx duplicate stealth addresses rejected within a block
5. Ring-size enforcement via monotonic `total_outputs_ever()`

All five are *tightening* rules. Honest miners producing well-formed blocks pre-activation continue to produce valid blocks post-activation — the fork is purely on the validation side. Mainnet (GA 2026-10-01) inherits these rules from genesis; no separate mainnet fork event.

52/52 consensus tests pass with activation flipped.

## What you need to know if you run a node

### Upgrade by 2026-06-28

The v1.0.12-rc1 binary is on the GitHub Releases page. Standard upgrade:

```bash
# Stop your node
sudo systemctl stop coincync-node

# Backup current binary
sudo cp /usr/local/bin/coincync-node /usr/local/bin/coincync-node.v1.0.11

# Drop in the new binary
sudo wget -O /usr/local/bin/coincync-node \
  https://github.com/Coincync/Coincync-Testnet-/releases/download/v1.0.12-rc1/coincync-node-v1.0.12-rc1
sudo chmod +x /usr/local/bin/coincync-node

# Verify signature
sha256sum /usr/local/bin/coincync-node
# Expect: 5d099719aceccb823684b586fb7274b5eee88051ffe3af0d1f66d186ccb9091b

# Restart
sudo systemctl start coincync-node
sudo journalctl -u coincync-node -f
```

### What happens at h=13_000

- **Automatic, no action required** if you're on v1.0.12-rc1
- **Pre-v1.0.12 binaries:** may briefly disagree on block validity at the fork height, but since the new rules only *tighten* (no honest block becomes invalid), the practical effect is "you should upgrade so YOU don't reject valid blocks the rest of the network is producing"
- Watch the chain tip on the explorer when h approaches 13_000

### If your node has trouble syncing

1. Check `tip_age_secs` via your local RPC — if > 600s, something's wrong upstream
2. Check `peer_count` — should be 3+ for healthy gossip
3. Open a thread in `#mining` or `#testnet` Discord — we monitor
