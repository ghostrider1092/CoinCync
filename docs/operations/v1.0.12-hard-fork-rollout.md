# v1.0.12 Hard Fork Rollout (Testnet)

**Activation:** testnet height **13_000** — approximately **2026-07-01** (could land 2-5 days later if hashrate dips; never before).

**Mode:** CIP-007 Mode A (static-height flag day). No BIP-9 signaling window.

**Net target:** TESTNET ONLY. Mainnet (GA 2026-10-01) ships with these rules from genesis — no separate mainnet activation event.

---

## What activates

Five consensus rules already forward-ported and dormant on main (PR #68, commits a582bbf0..d81be9e3):

1. **encrypted_amount tightened to exactly 8 bytes** — pre-fix accepted variable-length blobs; post-fork rejects anything else
2. **per-output size caps at block-level validation** — pre-fix caps only enforced at mempool admission; post-fork validator enforces at block-receive
3. **reject duplicate stealth addresses within a tx.outputs** — pre-fix silently accepted; post-fork rejected
4. **reject cross-tx duplicate stealth addresses within a block** — pre-fix silently accepted; post-fork rejected
5. **ring-size enforcement via monotonic `total_outputs_ever()`** — pre-fix used live UTXO-set size (race-prone); post-fork uses monotonic counter

All five are **tightening rules**: a v1.0.12-valid block is also v1.0.11-valid. Honest miners producing well-formed blocks pre-activation continue to produce valid blocks post-activation **without any binary change on the miner side**. The fork is purely on the validation side.

Miners running pre-v1.0.12 nodes only need to upgrade so they DON'T REJECT valid post-fork blocks (in case some other miner ships a block that exploits the v1.0.11 gaps and the v1.0.12-strict majority rejects it). Practically: just upgrade.

### T-5 days: build verify

```bash
git fetch origin && git checkout release/v1.0.12-rc1
cargo build --release --features testnet --bin coincync-node
scripts/verify-build.sh                     # reproducible-build check
shasum -a 256 target/release/coincync-node  # record for Discord
```

### T-3 to T-1: fleet upgrade (staggered)

**CRITICAL RULE:** Never restart all 5 fleet nodes within 10 minutes, even serially. Caused 2 partitions in one session previously. Use `sync-fleet-config.sh` + verify `peer_count >= 3 AND tip_age_secs < 300` BETWEEN hosts, not just `systemctl is-active`.

Order: `seed1` → `seed2` → `seed3` → `explorer` → `api`. Wait ≥ 30 minutes between hosts. Verify after each:

```bash
# On each host post-upgrade, before moving to next:
curl -s http://localhost:28081/rpc/testnet \
  -X POST -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"get_info","params":[]}' \
  | jq '{height, peer_count, tip_age_secs, is_synced, version}'

# Must show: peer_count >= 3, tip_age_secs < 300, is_synced: true,
# version: 1.0.12-rc1 (or later).
```

If any host fails the check, STOP. Roll back that host before continuing.

## Activation day (T)

### Monitoring

```bash
# Watch chain tip from any of the 5 fleet nodes:
watch -n 30 'curl -s https://api.coincync.network/rpc/testnet \
  -X POST -H "Content-Type: application/json" \
  -d "{\"jsonrpc\":\"2.0\",\"id\":1,\"method\":\"get_info\",\"params\":[]}" \
  | jq "{height, peer_count, tip_age_secs, total_difficulty}"'
```

Expect:
- `height` ticks up steadily (block every ~2-5 minutes per current testnet rate)
- `peer_count` stays at 5 across the fleet
- `tip_age_secs < 300` (no stalling)
- Around h=13_000, new rules become active. **If any fleet node's tip diverges**: STOP. The fork may not be coordinated.

### Crossing h=13_000

When the chain reaches h=13_000:
- v1.0.12 nodes validate new blocks against the tightened rules
- Pre-v1.0.12 nodes (if any remain) will accept post-fork blocks IFF they happen to satisfy the v1.0.11 ruleset (which all honest blocks do — see "tightening rules" above)

Run `get_info` on every fleet host. Compare `tip_hash` values. **All five must match.** If they don't, see Rollback.

### Post-activation audit (T+1 day)

- All 5 fleet nodes still on same tip
- No mempool admission errors related to the new rules in logs (`grep -E "encrypted_amount|stealth address|ring size" /var/log/coincync/*.log`)
- Community miner reports (`#mining` channel)

## Rollback procedure

If the activation goes sideways (chain splits, fleet diverges, repeated block rejections):

1. **DON'T panic-restart the fleet** — that violates the no-bulk-rolling-restart rule and made things worse historically.
2. **Identify the bad node(s).** Compare `tip_hash` across fleet via `get_info`. The minority is on the wrong fork.
3. **Coordinate via Discord** with miners — STOP MINING request.
4. **Roll the affected fleet hosts back to v1.0.11.x** (the pre-activation binary). Pre-v1.0.12 nodes will treat the fork as a soft tightening and continue accepting both rule sets.
5. **Triage the consensus bug** before re-attempting the fork at a future height.

**Last resort (chain split):** truncate the bad fork's tip and re-sync from the longest valid chain. Chaindata bootstrap from `seed1` per the standard incident playbook.

## What's NOT in this fork

The following items were considered for v1.0.12 but deferred:

- **BIP-9 signaling state-machine wiring** — gates added (PRs #70, #76, #77) but full activation logic not wired. Will land in a future fork that needs it.
- **MTP-in-ASERT** — defer to v1.0.13 or later. ASERT currently uses raw timestamps.
- **Merkle RFC 6962 leaf/node tags** — defer.
- **Graduated ring ramp (5 → 7 → 11 → 16)** — defer.
- **Fork-choice tiebreak (zebrad lowest-hash pattern)** — defer to next testnet fork after this one.

All deferrals tracked in `[deferred_audit_items_ship_schedule.md]` (operator memory).

## Prior art

Bitcoin Core's flag-day activations (BIP 16, BIP 30, BIP 34, BIP 65, BIP 66) all used static-height activation for the same operator-coordination reason. BIP-9 signaling was added later for changes where miner readiness was uncertain — not the situation for an operator-controlled 5-node testnet fleet.

Monero's hard forks (historically every 6 months pre-2022) follow the same pattern: announce, schedule, flip a height constant, deploy. Mode A is the conservative default.
