# CoinCync v1.0 Mainnet Audit Preparation

**Audience:** Audit firm scoping the v1.0 base-chain mainnet release.
**Source-of-truth this document points at:** the `coincync` root crate + four v1.0 supporting crates (~73 000 LOC implementation + tests) at the commit identified in §0. Created 2026-05-21.

This file is **not** the spec. The spec is the [Constitution](../CONSTITUTION.md), the [Bill of Rights](BILL_OF_RIGHTS.md), and the [CIP register](cip/README.md). The roadmap (what ships when) is [docs/roadmap.md](roadmap.md), and the cross-cutting technical update log is [docs/BLOCKCHAIN_ROADMAP.md](BLOCKCHAIN_ROADMAP.md). This document is the **wayfinding layer**: it tells an incoming auditor which file holds what, which tests exercise which property, which surfaces carry the highest cryptographic risk, and how the perimeter is bounded against the v1.1 (cyncswap) and v1.x+ (Orchard, CyncHub) scopes that are deliberately *not* in this audit.

The cyncswap audit-prep companion document is [docs/cyncswap-audit-prep.md](cyncswap-audit-prep.md) — that audit happens after this one, on its own engagement (~30 days post-mainnet ship). See [decisions/2026-05-20-staged-mainnet-and-cyncswap.md](decisions/2026-05-20-staged-mainnet-and-cyncswap.md) for the staging rationale.

## 3. Consensus layer

**Block validation.** [src/consensus/validation.rs](../src/consensus/validation.rs) `validate_block` is the sole authority on whether a block is valid. The function composes header validation, PoW check, transaction-level validation (which composes the crypto primitives above), and reorg-defense checks (CIP-009 layers 1–6).

**Critical-files lockfile gate.** The eight files in [critical_files.lock](../critical_files.lock) — `CONSTITUTION.md`, `docs/BILL_OF_RIGHTS.md`, `src/testnet.rs`, `src/constants.rs`, `src/consensus/difficulty.rs`, `src/consensus/pow.rs`, `src/consensus/validation.rs`, `src/emission/curve.rs` — are SHA-256-protected. The build script in [build.rs](../build.rs) refuses to compile if any hash drifts. Refresh requires running `COINCYNC_REGEN_LOCK=1 cargo run --locked --bin update-critical-hashes`. **The auditor should grep `critical_files.lock` for any change in the audited diff against the prior tag and treat it as a consensus rule change.**

**Reorg defense (CIP-009).** Six layers, design at [docs/security/reorg-defense.md](security/reorg-defense.md). Layers 1–3 active in production. Layer 4 (rolling soft-finality, CIP-009.D) is the `coincync-rolling-finality` crate, feature-gated and dormant in v1.0 mainnet pending activation per CIP-011. Layers 5–6 cover specific deep-reorg recovery scenarios.

**Difficulty algorithm (DAA).** Dual-anchor ASERT (Adjusted Selective Recursive Target) at [src/consensus/difficulty.rs](../src/consensus/difficulty.rs). Short + long window anchors blended via weighted combination. `MIN_DIFFICULTY` floor caps ASERT below the unsafe range where block production outruns P2P propagation. Emergency drop multiplier for long stalls.

**Property tests.** Across `tests/property_invariants_*.rs` in the crate root and within each module's `tests` block:

- `tests/property_invariants_amount.rs` — Amount arithmetic invariants (saturating + checked).
- `tests/property_invariants_hash.rs` — Hash type roundtrip + canonical encoding.
- `tests/property_invariants_address.rs` — Address parsing + bech32 roundtrip.
- `tests/property_invariants_keys.rs` — Key derivation determinism + zeroization.
- `tests/property_invariants_validator.rs` — Transaction validation rule invariants.
- `tests/property_invariants_difficulty.rs` — DAA monotonicity + bounded adjustment ratio.
- `tests/property_invariants_stealth.rs` — Stealth-address ECDH roundtrip.
- `tests/property_invariants_memo.rs` — Encrypted-memo decrypt-after-encrypt fidelity.

## 6. Conceptual clarifications the audit should be aware of

### 6.1 What v1.0 ships vs what is deliberately deferred

The staged-mainnet decision (see [decisions/2026-05-20-staged-mainnet-and-cyncswap.md](decisions/2026-05-20-staged-mainnet-and-cyncswap.md)) puts cyncswap (CIP-001 atomic swap) into v1.1 with its own audit, and the Orchard shielded pool into its own later v1.x release with its own audit. The v1.0 binary excludes the cyncswap crate by default — `cargo build` of `coincync-node` does not pull `coincync-swap` into the dependency graph. The Orchard primitives in `crates/orchard-side/` are present in source but are not reachable from any v1.0 code path. The auditor should verify these scope boundaries hold by tracing the dependency closure from each v1.0 binary entrypoint.

The cyncswap audit ships its own prep doc at [docs/cyncswap-audit-prep.md](cyncswap-audit-prep.md), which the auditor should NOT use as a substitute for this one — the two engagements are independent.

### 6.2 ScopedViewKey is a feature, not a leak

[src/wallet/key_epoch.rs](../src/wallet/key_epoch.rs) `ScopedViewKey::to_json` deliberately serializes the `view_secret` to a JSON string. This is **by design** — `ScopedViewKey` is CoinCync's time-scoped selective-disclosure innovation (Article IX's "view keys" facility); the operator hands the JSON to an auditor or tax authority to selectively reveal transactions within a specific block-height range. The docstring explicitly warns "contains view secret — handle carefully." The audit should treat the export path as in-scope for *correctness* (does the receiver actually only learn what is in-scope?) but not as a "leak."

### 6.3 Rolling finality is dormant in v1.0

The `rolling-finality` Cargo feature is OFF in the default v1.0 mainnet build. The [src/consensus/rolling_finality.rs](../src/consensus/rolling_finality.rs) adapter module and the [crates/coincync-rolling-finality/](../crates/coincync-rolling-finality/) crate are present so the integration can be reviewed and tested ahead of the CIP-011 activation decision. **Activation heights (testnet 50 000 ENABLE, 75 000 ENFORCE; mainnet 25 000 / 50 000) are constants but the consensus rule that consults them is not wired into `validate_block` — that wiring lands in a later, audit-coordinated commit.** The auditor's review of CIP-009.D should treat the machinery as reviewable but not active.

### 6.4 Phase-2 stores are wired but not appended

The shielded-pool, Spark, and kernel-aggregation stores in [src/storage/](../src/storage/) ship in v1.0 with their reorg-rewind machinery wired into the chain-apply path. **They are not appended to** — `cargo build` produces a binary whose chain state never adds entries to `ShieldedStore`, `SparkStore`, or `KernelStore`. They sit at length 0 with a `REWIND READY` posture, ready for the Phase-2 hard fork to begin populating them. The dormant code is in-tree for two reasons: (a) keeping the storage layer's reorg-handling code uniform avoids a future hard-fork that has to *also* change the storage layer; (b) operators running pre-fork can verify their binaries reproduce byte-for-byte against a post-fork-ready reference. **The auditor should verify the dormant stores are not reachable from any v1.0 code path that mutates them, and that their `rewind` semantics are sound under future activation.**

### 6.5 v3 wallet file format is the current state

Wallet files use the v3 format defined in `src/wallet/persistence.rs`. The format authenticates the encrypted payload (AEAD tag) and validates KDF header parameters against fuzz-discovered bounds before deriving the key, but it does NOT cover the KDF parameters themselves under an HMAC. A v4 format with HMAC over `(header‖nonce‖ct)` and an independent MAC key is designed at [docs/security/wallet-file-v4-design.md](security/wallet-file-v4-design.md) but is **unscheduled future-work** — *not* slotted for v1.0 mainnet, the v1.0.x point-release stream (bug fixes only), or v1.1 (which ships cyncswap only). The audit should treat v3 as the audited format and may review the v4 design as a documented evolution; an attacker who can write arbitrary bytes to the wallet file can already cause decryption failure (the AEAD tag fails), but they cannot pivot that into a brute-force key-derivation oracle because the KDF params are bounded. The v4 work specifically closes the header-tampering timing channel — see the design doc §1 for the full threat model.

## 8. Test-coverage gaps (knowingly missing)

Auditor should know:

- **Cross-implementation vectors are limited to in-tree generation.** Unlike Bitcoin's BIP-340 test vectors which are reference-implementation-derived, the CoinCync vectors are generated by this codebase. The audit firm may want to derive vectors independently using the upstream `curve25519-dalek` / `blake3` / etc. crates directly and confirm equality. The codebase intentionally uses well-known primitives (no homemade crypto) so independent verification is straightforward.
- **Mutation testing not yet run against the base chain.** The cyncswap audit (separate engagement) achieved 100% mutation score on its 4 crypto-critical files via cargo-mutants. The base chain has not yet been put through the same exercise. **This is a deliberate item for the audit team to flag if they want an additional pre-engagement assurance pass; the configuration at [.cargo/mutants.toml](../.cargo/mutants.toml) can be extended to cover base-chain modules.** Estimated cost: ~3–5× the cyncswap runtime due to perimeter size.
- **Line coverage not yet measured workspace-wide.** The cyncswap crate's `cargo llvm-cov` numbers (97% line coverage) are documented in [docs/cyncswap-coverage-2026-05-20.md](cyncswap-coverage-2026-05-20.md). The base chain has not been measured. The audit team may want this as part of pre-engagement scoping.
- **No `unsafe` audit beyond the RandomX FFI boundary.** Other `unsafe` usage in the workspace should be enumerated (`rg "unsafe" --type rust`). Expected count: low (most `unsafe` is in upstream crates), but the auditor should produce a definitive list.
- **No formal-methods proofs.** The protocol is documented prose + property-tested code. No machine-checked proofs of consensus rules.
- **Live multi-region mainnet stress** is the 60-day testnet soak listed in [docs/roadmap.md](roadmap.md) v1.0 shippable bar — runs from the audited-commit tag to the mainnet ship date.

### 11.2 False-positive patterns observed during the session

The session also surfaced consistent classes of agent-claimed bugs that turned out to be design intent, defended elsewhere, or simple confabulation. The auditor may find these patterns useful to recognise:

- **`SystemTime::now().duration_since(UNIX_EPOCH).unwrap_or_default()`** — fail-closed defaults that produce `0 seconds since epoch`. Used at multiple sites in `chain.rs`, `consensus/pow.rs`, `crypto/disclosure.rs`. Treating these as "panic risks" was incorrect; they are the correct defensive idiom for "system clock pre-1970."
- **`compare_and_swap` calls misread as loops.** [src/db/utxos.rs:131](../src/db/utxos.rs) was claimed to be an "unbounded CAS loop"; in fact it is a single-shot CAS that returns `Ok(false)` on contention.
- **Closure-borrow lifetime extension.** [src/wallet/mnemonic.rs:78](../src/wallet/mnemonic.rs) `for_each_word(F: FnMut(&str))` was claimed to allow references to escape; in fact Rust's borrow checker enforces the lifetime.
- **"Validate is run per unlock" framed as a performance bug.** [src/wallet/persistence.rs:189-247](../src/wallet/persistence.rs) `validate()` is three comparisons; running it per-unlock is the correct defense-in-depth.
- **P2P listen-addr defaulting to `0.0.0.0`** was flagged as a posture issue; in fact P2P nodes by design need to accept inbound connections.
- **CLSAG aggregate-coefficient computation** was challenged on canonical-scalar grounds; in fact it uses `from_canonical_bytes` correctly and rejects non-canonical encodings (and `ct_eq` everywhere).

The auditor's own review will inevitably re-surface some of these. This document does not ask the auditor to take the disposition on trust — it lists them so a verification check (rather than a fresh investigation) is the natural response.
