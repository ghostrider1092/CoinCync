# v1.0.10 5-day sandbox soak — procedure

> **What this is.** A 5-day continuous-run test of the v1.0.10 binary
> against the live testnet with the `MIN_OUTPUT_AGE` hard fork
> activation height ARMED (not just placeholder). The soak catches
> latent interactions between the new 100-block maturity rule and the
> wallet `unlock_height` / mempool age checks that unit tests can't
> surface — and that only show up when blocks are actually being
> produced over wallclock time.
>
> **Why 5 days.** The hard-fork activation height is set to current
> testnet tip + 5000 blocks ≈ 7 days at 120s. A soak shorter than the
> activation window risks shipping a tag that goes through activation
> before the soak proves the activated rule works. 5 days is the
> minimum that exercises the rule across the activation boundary on
> the sandbox.
>
> **Where this runs.** On a dedicated sandbox node — NOT a production
> seed/miner. Pick a Vultr VM with ≥4 GB RAM (RandomX fast mode needs
> ~3 GB) and ≥40 GB disk. The sandbox should have its own
> wallet+miner so we can exercise the spend path under the new rule.

---

## Pre-soak setup (one-time, T-7 days)

### 1. Provision the sandbox

```powershell
# From your local machine. Use a dedicated soak VM, not a production seed.
# Vultr 4 GB / 2 vCPU / Ubuntu 22.04 is the minimum for fast-mode RandomX.
```

### 2. Arm the hard-fork height on a soak branch

```powershell
cd C:\dev\coincync
git checkout -b soak/v1.0.10-armed
.\scripts\arm-min-output-age-fork.ps1
# Confirms tip, computes activation height, edits constants.rs +
# critical_files.lock. Don't push this branch — the soak is local.
```

Note the activation height printed by the script — you'll watch for
it during the soak.

### 3. Build the soak binary

```powershell
cargo build --release --features randomx
# Output: target/release/coincync-node (+ coincync-rig, coincync-wallet)
```

Copy the binaries to the sandbox VM along with `target/release/SHA256SUMS`
(generate locally so you can verify the sandbox is running exactly the
soak binary, not a stale one).

### 4. Wipe the sandbox's chain data + restart syncing

```bash
# On the sandbox VM
systemctl stop coincync-node
rm -rf ~/.coincync-testnet/chain  # nuke local chain state
# Don't delete the wallet — we want a wallet with history to exercise
# the spend path against the soak binary.
systemctl start coincync-node
```

The sandbox will IBD-sync from the live testnet. Initial sync time
~30-60 min depending on chain depth.

## During-soak monitoring (T+0 through T+5 days)

Run the soak monitor every ~6 hours, or set it up as a cron job for
continuous logging. The monitor captures all the signals into a
structured log that's easy to diff for anomalies.

```powershell
.\scripts\soak-monitor.ps1                            # one-shot run
.\scripts\soak-monitor.ps1 -CsvAppend soak-2026-06.csv  # append to trend log
```

The script captures:

- **Chain health:** tip height, tip age (seconds since last block), difficulty trend
- **Mempool:** size, oldest entry age (catches stuck-mempool-tx bugs around the maturity rule)
- **Peer count:** drops below 5 = sandbox is losing connectivity (real bug or operator misconfig)
- **Reorg counter:** any reorg during the soak is interesting; deep reorgs are FAILURE
- **Wallet balance:** total + spendable (must converge once outputs mature)
- **Pending-maturity error rate:** if the sandbox wallet tries to spend and the activation guard rejects, the error should match expected behavior at the current height vs activation height
- **RandomX mode:** must be `full-mem` on a 4 GB sandbox (else the soak is testing the wrong path)
- **Process memory:** baseline + growth rate (~2.5 GB RandomX dataset + ~200 MB chain state expected)

### What "soak passing" looks like

After 5 days continuous run:

- ✅ Chain advanced ~3600 blocks (5 days × 24h × 30 blocks/h, allowing for some variance)
- ✅ Tip age never exceeded 30 minutes (sandbox stayed in sync)
- ✅ Mempool oldest entry never exceeded 4 hours (no stuck txs)
- ✅ Peer count stayed ≥5 throughout
- ✅ Zero deep reorgs (depth > 10 blocks)
- ✅ Process memory plateau ~3 GB, no leak trend
- ✅ Sandbox wallet exercised the spend path at least once across the activation height
- ✅ All spend-path attempts produced the expected outcome (success when output age ≥ rule-at-height, `BalancePendingMaturity` otherwise)

### What "soak failing" looks like

Any one of these is a NO-GO for the tag cut:

- ❌ Deep reorg (depth > 10) — investigate before tagging
- ❌ Memory growth >100 MB/day after the initial 4 GB plateau (RandomX dataset or chain state leak)
- ❌ Mempool oldest entry > 6 hours sustained (stuck-tx bug)
- ❌ Spend path returns wrong error type (e.g. `InsufficientBalance` instead of `BalancePendingMaturity` for a maturity-window failure)
- ❌ Sandbox falls out of sync repeatedly (tip age > 30 min more than 3× in the soak window)
- ❌ Panic, crash, or process restart — investigate root cause regardless of severity

### What "soak inconclusive" looks like

- ⚠ Single transient drop (peer count temporarily 0 due to upstream connectivity, etc.) — fine if it recovers within an hour
- ⚠ One spurious mempool age spike — fine if it self-resolves
- ⚠ Reorg of depth 2-5 around the activation height — POSSIBLE if multiple chains are racing at activation. Document but don't fail the soak.

## Post-soak — exercising the activation boundary

The soak's most valuable hour is the one where the chain CROSSES the
activation height. The wallet, mempool, validator, and miner all see
the rule flip in real time.

If the natural chain progress crosses the activation height during
the soak: great, monitor closely for 1 hour each side of the boundary.

If activation height is still 100+ blocks in the future at T+5 days:
either extend the soak by a couple of days OR re-arm the height to
sandbox-tip + 50 blocks for a focused boundary test (separate from
the general soak).

### Boundary exercise checklist

In the hour around activation height ± 50 blocks:

1. Send a tx FROM the sandbox wallet whose input coinbase is exactly
   10-99 blocks old. Pre-fork: should succeed. Post-fork: should
   error with `BalancePendingMaturity { blocks_to_wait: N }` where
   N is approximately `(100 - input_age)`.
2. Watch the sandbox mempool. Any tx that was admitted under
   pre-fork rules but is now invalid under post-fork rules MUST be
   evicted (or shadow-evicted; flagged TBD in v1.0.10) before its
   first inclusion attempt.
3. Watch the validator log. Any inbound block with a coinbase spend
   under 100 blocks old at the activation-height-or-above MUST be
   rejected with `InvalidTransaction` referencing the maturity rule.
4. Confirm the explorer shows the rule transition correctly. The
   privacy-stats page reads activation height live; spot-check it.

## Soak failure recovery

If the soak fails on any of the FAIL criteria above:

1. **Stop the sandbox immediately** and capture the full chain state
   (`tar czf sandbox-state-$(date +%Y%m%d-%H%M).tar.gz ~/.coincync-testnet`)
   for forensic analysis. Don't restart on the same state — too easy
   to lose the failure repro.

2. **File a GitHub Issue** with the captured state attached (use the
   bug-report template; set the label to `consensus-blocker`).
   Tag the v1.0.10-CHECKLIST.md as the blocking release.

3. **Do NOT tag v1.0.10** until the issue is resolved. The soak's
   whole point is to surface the bugs that ship-day testing can't.

4. **Re-soak** after the fix lands. Don't shortcut the soak the second
   time — give it the full 5 days again. Two failures in a row
   indicate the activation height itself should be pushed out farther
   to give the team more cycles.
