# v1.0.10 hard-fork rollback plan

> **When to use this doc.** A critical bug surfaces in the v1.0.10
> consensus path AFTER the `MIN_OUTPUT_AGE` 10 → 100 hard fork has
> activated on testnet, and the right call is to back out the fork
> rather than ship a forward-fix.
>
> **When NOT to use this doc.** Bugs in non-consensus paths
> (wallet UI, RPC, observability). Those ship as a v1.0.10.1 point
> release with no coordination. This doc is only for the hard-fork
> rule itself.

---

## Decision tree (run this in under 30 minutes)

```
Critical bug observed post-activation?
├── Is the bug in the MIN_OUTPUT_AGE rule itself?
│   ├── NO → it's not a hard-fork bug. Ship a point release. Use
│   │       the standard upgrade flow. STOP — do not use this doc.
│   │
│   └── YES → continue.
│
├── Is the bug exploitable in the next 24 hours (e.g. lets an
│   attacker double-spend, mint inflation, or fork the chain)?
│   ├── YES → IMMEDIATE rollback. Skip §1; jump to §2.
│   │
│   └── NO → still rollback, but on the 12-hour timeline in §1.
│            Coordinate with operators first.
│
└── If you're unsure: TREAT AS YES.
```

The activation-guard design makes rollback cheap: flipping
`MIN_OUTPUT_AGE_HARDFORK_HEIGHT` back to `u64::MAX` returns the
chain to pre-fork behavior at the next node restart. There is no
state migration, no UTXO re-indexing, no wallet re-scan. The
buggy code path becomes unreachable.

## §1. Coordinated rollback (12-hour timeline)

Use when the bug is real but not immediately exploitable. Gives
operators a full upgrade window.

### T+0 — confirm + announce

1. **Open a GitHub Issue** titled
   `[ROLLBACK] v1.0.10 hard fork — <one-line description>` with
   the bug repro, the affected commit, and the proposed rollback
   plan. Link it from `#announcements` immediately.

2. **Post in Discord `#announcements`:**

   > ⚠️ **v1.0.10 hard fork rollback in progress.** A bug has
   > been identified in the `MIN_OUTPUT_AGE` consensus path. We
   > are reverting the activation. New release v1.0.10.1 will ship
   > within 12 hours. **Do not upgrade away from v1.0.10 yet** —
   > we'll post the upgrade instructions in this channel.

3. **Notify the audit firm** if engagement is active. They need
   visibility into rollbacks.

### T+1h — prepare the rollback PR

Create branch `rollback/v1.0.10.1`:

```powershell
git checkout main
git pull --rebase origin main
git checkout -b rollback/v1.0.10.1
```

In [src/constants.rs](../../src/constants.rs), revert the testnet
`MIN_OUTPUT_AGE_HARDFORK_HEIGHT` constant to `u64::MAX`:

```rust
#[cfg(feature = "testnet")]
pub const MIN_OUTPUT_AGE_HARDFORK_HEIGHT: u64 = u64::MAX;
```

Refresh `critical_files.lock` via the build-error trick (or via
`cargo run --bin update-critical-hashes` if the build itself is
clean). Commit:

```
consensus: ROLLBACK v1.0.10 MIN_OUTPUT_AGE hard fork

Reverting MIN_OUTPUT_AGE_HARDFORK_HEIGHT from {ACTIVATED_HEIGHT}
back to u64::MAX for v1.0.10.1-testnet. Bug surfaced
post-activation: <one-paragraph>. See GitHub issue #N for full
details.

Forward-fix planned for v1.0.11 after the underlying issue is
resolved.

ZERO CHAIN STATE CHANGE. The activation-guard helper returns the
pre-fork value (10) when `current_height < MIN_OUTPUT_AGE_
HARDFORK_HEIGHT`, so this commit restores pre-fork behavior at
the next node restart. No reorg, no UTXO re-index, no wallet
re-scan.
```

Run the full pre-tag checklist on the rollback branch — same as
for the original tag — to make sure the revert doesn't ship a
broken binary.

### T+3h — push the rollback

```powershell
git push origin rollback/v1.0.10.1
gh pr create --title "ROLLBACK v1.0.10.1 — revert MIN_OUTPUT_AGE hard fork" `
  --body "See GitHub issue #N for the underlying bug. Reverts MIN_OUTPUT_AGE_HARDFORK_HEIGHT to u64::MAX. Zero chain state change."
```

Merge after CI green. Tag immediately:

```powershell
git checkout main
git pull --rebase origin main
git tag -s v1.0.10.1-testnet -m "Rollback of v1.0.10 hard fork — see #N"
git push origin v1.0.10.1-testnet
```

GitHub release with the rollback rationale in the body; reuse the
[v1.0.10 SHA256SUMS dance](v1.0.10-CHECKLIST.md#7-launch-day-coordination)
for the new binaries.

### T+6h — coordinated operator upgrade

Post in `#announcements`:

> 🚨 **v1.0.10.1-testnet (ROLLBACK) is out.** Download:
> <release URL>. **Stop your node, replace the binary, restart.**
> No data migration. The chain stays on its current tip; the
> rollback only affects which rule the validator applies going
> forward.
>
> The chain will return to pre-fork `MIN_OUTPUT_AGE = 10` at the
> next block your upgraded node validates. There is no
> activation height for the rollback — it's effective immediately
> on the upgraded node.
>
> **You MUST upgrade.** Continuing to run v1.0.10 means rejecting
> the post-rollback blocks the network produces.

### T+12h — verify fleet upgrade

Run the operator-upgrade-tracking script (`scripts/peer-versions.ps1`
once it exists, see [v1.0.10-CHECKLIST.md](v1.0.10-CHECKLIST.md)).
Target: ≥80% of seed/miner fleet on v1.0.10.1.

If <80%: post again in `#announcements`, ping individual operators
in DMs. The cost of running with 20% on the wrong rule is small
(they're just behind the tip), but it's measurable orphan-rate
damage to the testnet metrics.

## §2. Emergency rollback (T+0 to T+90 minutes)

Use when the bug is immediately exploitable. Skip the 12-hour
operator window — ship the rollback as fast as the test suite
allows.

### Minute 0: pull the trigger

Skip the GitHub Issue ceremony — drop straight into the rollback
branch from §1. Tag and push within 90 minutes.

### Minute 5: Discord announcement (terse)

> 🚨🚨🚨 **EMERGENCY: v1.0.10 hard fork is being rolled back due
> to a critical exploit.** Stop all mining and node operations.
> Do NOT broadcast transactions. Upgrade instructions within
> 90 minutes.

### Minute 30: get the rollback binary out

Even if CI takes 30 minutes — push the tag, push the release with
binaries, post the upgrade instructions. Skip the "GitHub release
description" niceties; the rationale goes in a follow-up commit
to the release notes.

### Minute 90: post upgrade instructions

Same as the §1 T+6h instructions, but accelerated. Once posted,
monitor `#announcements` for operator confirmations.

1. **Write a post-mortem** at `docs/launch/v1.0.10-postmortem.md`.

   `MIN_OUTPUT_AGE` activation guard. Reuse the same activation-

   second time.

## §4. What NOT to do during a rollback

- **Don't try to write a forward-fix in the rollback window.** A
  forward-fix that ships in v1.0.10.1 instead of a rollback
  doubles the chance of shipping a SECOND bug. The hard-fork
  rollback is cheap; use it.
- **Don't `git push --force` to main during the rollback** — the
  rollback is a real commit on top of the existing history, not a
  rewrite. The audit firm needs to see the rollback in
  `git log`, not "history disappeared."
- **Don't skip the SHA256SUMS publication** even if you're rushing.
  Operators verify the rollback binary too.
- **Don't pull the activation-guard helper out of the code** as
  part of the rollback. Leave the structural code in place;
  flipping just the constant back to `u64::MAX` is the minimum
  surgery. The forward-fix will set it to the new chosen height
  with the bug-fixed code.
- **Don't go quiet on Discord** during the rollback window.
  Operators will be confused; visibility matters more than
  polish. Post status updates every 30-60 minutes until the
  rollback binary is out.

## Why this rollback is cheap (audit-firm reference)

The MIN_OUTPUT_AGE activation guard is intentionally a single
constant + a height-keyed helper. There is no state migration
when the rule activates, and there is no state migration when it
deactivates. Specifically:

- **No UTXO re-indexing.** Outputs are stored with their landed
  height; the maturity check is computed against the current
  validation height + the helper. Both rules use the same input
  fields.
- **No wallet re-scan.** The wallet's `unlock_height` field on
  past `TransactionRecord` entries was computed at the rule in
  force when the output landed; that value is correct under
  either rule (pre-fork: 10-block unlock; post-fork: 100-block
  unlock). Either way, the unlock_height is honored by the
  current validator at spend time. There is no "now wrong" data
  in the wallet.
- **No mempool flush.** Mempool entries hold transactions whose
  input coinbase outputs are checked against the current rule
  when the entry is admitted AND when the entry is later included
  in a block. A rule flip just changes which value the check uses
  — the txs themselves are still valid wire-format objects.

The only state that changes between the two rules is the
**accept/reject decision on a few in-flight transactions whose
input coinbases are between 10 and 100 blocks old.** Those will
either succeed under the rollback (pre-fork) or fail and need
to be rebroadcast after coinbase maturity catches up. This is
recoverable per-tx; not chain-level.
