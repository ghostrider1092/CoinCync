> consensus rule change (hard fork), one consensus-critical refactor
> (validator↔fee_market dedup), one real secret-leak SECURITY fix,

## 3. Candidate items (ship if ready, defer otherwise)

Ordered by ROI and how close to "done" each one is.

### RandomX fast-mode (Phase 2) — kill the Mutex bottleneck

The current VM_CACHE is a single global VM behind a `parking_lot::Mutex`
(see [src/consensus/pow.rs:286](../../src/consensus/pow.rs)). All hash
calls serialize through it — kills mining parallelism. With 4 mining
threads each calling `compute_pow_hash`, only 1 runs at a time.

The fix: shared global dataset, per-thread VMs.

```
DATASET_CACHE: Mutex<Option<(seed, Arc<RandomXDataset>)>>  ← built once per epoch (30-60s)
thread_local! { VM_CACHE: RefCell<Option<(seed, RandomXVM)>> }  ← per-thread, ~ms to build from dataset
```

- Each thread builds its own VM from the shared dataset (~ms)
- Hash calls go through the thread-local VM, no Mutex contention
- N mining threads → N× aggregate throughput

Size: 1-2 focused days. Bigger refactor than Phase 1 — touches the
hash dispatch path. Lockfile-touching (pow.rs again). Worth shipping
in v1.0.10 if Phase 1 lands clean and we have time. **Owner: this
session or next; flag for v1.1 if pre-tag window gets tight.**

## 7a. Operator upgrade tracking (gates the activation decision)

Before activating the hard fork, confirm that ≥80% of the seed +
miner fleet is on v1.0.10. Forking off 20% damages testnet metrics
and operator trust.

```powershell
.\scripts\peer-versions.ps1                     # default: ≥80% on v1.0.10
.\scripts\peer-versions.ps1 -Threshold 90       # stricter
.\scripts\peer-versions.ps1 -TargetVersion 1.0.10 -TimeoutSec 8
```

The script discovers peers via `get_peers` against each seed, then
polls each peer's `get_info` for the version string. Reports
upgraded % vs the threshold; exits with code 0 (safe), 1 (script
error), or 2 (below threshold — DO NOT ACTIVATE). Outdated peers
are listed by address so they can be DMed in `#mining`.

Re-poll every 48h until the threshold is met. If 5+ days pass and
the fleet still isn't at threshold, postpone the activation height
by re-arming with a larger buffer:

```powershell
.\scripts\arm-min-output-age-fork.ps1 -Buffer 10000  # 2× standard
```

## 7b. Rollback plan (if a critical bug surfaces post-activation)

See [v1.0.10-ROLLBACK-PLAN.md](v1.0.10-ROLLBACK-PLAN.md) for the
full procedure. Summary: the activation guard is a single constant
+ a height-keyed helper, so flipping `MIN_OUTPUT_AGE_HARDFORK_HEIGHT`
back to `u64::MAX` and shipping a v1.0.10.1 returns the chain to
pre-fork behavior with **zero state migration** (no UTXO re-index,
no wallet re-scan, no mempool flush).

Two timelines documented:

- **Coordinated rollback (12h):** non-exploitable bugs. Operators
  get a full upgrade window.
- **Emergency rollback (90min):** immediately-exploitable bugs.
  Skip the ceremony, ship the rollback binary, post terse Discord.

The rollback plan also covers what NOT to do (forward-fix instead
of rollback, force-push to main, skip SHA256SUMS) and includes the
audit-firm-visible "why this rollback is cheap" reference section.

## 8. Risk register (what to watch for during the cut)

- **Hard fork upgrade lag.** If <80% of seed/miner fleet upgrades
  before activation height, the chain forks. Mitigation: 5-day
  activation buffer + loud Discord announcement.
- **RandomX fast-mode RAM pressure.** Hosts with exactly 3 GB free
  may hit edge cases where dataset alloc succeeds but the OS later
  OOM-kills the process. Mitigation: opt-out env var documented;
  fallback to light mode if dataset alloc fails (loud warning
  surfaces this).
- **AddressInfo.balance removal breakage.** If any external tool
  was deserializing the `balance` field from the JSON shape (even
  though we never returned it), they'll see a missing-field error.
  Mitigation: the struct was never constructed in our code, so no
  shape ever shipped with the field; risk is theoretical only.
- **View-key SECURITY fix surfacing pre-existing leaks.** The fix
  is forward-only (new ViewKey instances zeroize on drop); it
  doesn't retroactively scrub memory from past sessions. If an
  operator had their machine compromised at any point pre-upgrade,
  view-key material may have been recoverable. Mitigation: the
  release notes should be honest about this — recommend rotating
  view keys post-upgrade for paranoid operators.
- **MIN_OUTPUT_AGE soak surprises.** A 10× longer maturity window
  could expose latent assumptions in the wallet UTXO selector that
  the existing 10-block window was masking. Mitigation: that's
  what the 5-day soak is for.
