**🔴 SECURITY FIX (call this out)**
═══════════════════════════════════════════

**View-key forward secrecy was broken.** The `ViewKey` struct claimed to zero its secret material on drop via `ZeroizeOnDrop`, but the secret field had `#[zeroize(skip)]` on it with an in-line comment claiming "skip only applies to non-secret fields; key_data IS zeroized via the struct derive." That comment was dead wrong — verified against the zeroize_derive v1.4.x macro source. Skipped fields are EXCLUDED from the generated Drop. So view-key material was lingering in process memory past the Drop boundary, recoverable from a core dump or memory-read primitive.

Forward-only fix: removed the skip attribute on `key_data`. New `ViewKey` instances created post-upgrade get the actual forward-secrecy guarantee. Existing view keys created before upgrade are unaffected by the fix — paranoid operators may want to rotate view keys post-upgrade.

Originally mis-classified L-severity in the audit-prep punchlist; should have been H. The audit firm will see this isolated in commit `36d5636`.

**WHAT LANDED**
═══════════════════════════════════════════

**`MIN_OUTPUT_AGE` 10 → 100 — coordinated hard fork** ← THE HEADLINE

Coinbase maturity tightens from 10 blocks (~20 min) to 100 blocks (~3.3 hours). The 10× increase closes the practical-attack window where a deep-reorg adversary could double-spend a 10-block-confirmed output by privately mining an 11-block sidechain. At 100 blocks that adversary needs ~2 hours of >50% hashpower instead of ~20 min — a real economic step-up in attack cost.

Activation guard is height-keyed: blocks BELOW activation use the old 10-block floor; blocks AT OR ABOVE use the new 100-block floor. Backwards-compat block replay validates clean. All 16 call sites across the validator, wallet selection, send paths, and history display read from the same `min_output_age_at_height(height)` helper — no possibility of validator/wallet divergence at the boundary. Dedicated boundary-test in `src/constants.rs` locks the `<` vs `>=` semantics so an audit-time off-by-one would be caught immediately.

**RandomX — Phase 1 (fast mode)**

Full-mem mode is now the default. Allocates a 2 GB dataset (~30-60s one-time per epoch, every 2048 blocks) and gets 5-10× per-hash throughput vs the previous light-mode cache-only path. Hosts with <3 GB free fall back automatically to light mode with a loud operator-visible warning (no silent degradation). Opt-out via `COINCYNC_RANDOMX_LIGHT_MODE=1` for operators who'd rather skip the dataset build.

Bit-identical proof: a dedicated `fast_light_equivalence` test confirms full-mem and light-mode produce identical hashes for the same (seed, input) pair. Verified in 43.91s in our CI environment. No consensus split between full-mem miners and light-mode verifiers — RandomX's whole spec guarantees this, and our wiring is correct.

**RandomX — Phase 2 (per-thread VMs)**

The previous design was one global RandomXVM behind a Mutex — every hash call serialized through it. With N mining threads, you got 1× throughput regardless of `--threads`. The Mutex bottleneck was almost certainly the cause of the "35 H/s on Windows" reports a few days back.

Phase 2 replaces it with a shared `DatasetEntry` behind a `parking_lot::RwLock` + per-thread VMs via `thread_local!`. The cache + dataset are Arc-internally so cheap to clone; per-thread VM construction is ~ms once the dataset is built. Hot path is now a thread-local read — zero contention.

Expected real-world impact: **aggregate hashrate now scales linearly with `--threads`**, AND each per-hash is 5-10× faster from phase 1. Combined, that's roughly N × 5-10× of the v1.0.9 baseline. For a 4-thread machine in fast mode: ~20-40× the v1.0.9 hashrate.

Two new ignored tests validate Phase 2 correctness: `concurrent_threads_consistent_hashes` (N threads hashing the same input must all match a single-thread baseline) and `epoch_rotation_rebuilds_thread_vms` (different seeds produce different hashes; same seed round-trips).

**RandomX — operator visibility (shipped earlier in 74b212b, recap here)**

The "35 H/s hashrate" Discord report from @member surfaced a silent-fallback path: when RandomX couldn't initialize JIT (typically Windows Defender blocking the JIT memory page), the miner fell back to interpreted mode at `info` log level. Operators didn't watch info-level logs and had no signal that they were running 100× slower than possible. Now you get a giant red banner in the terminal that tells you exactly what to do (add the binary to AV exclusions). Same treatment for the JIT-only intermediate fallback (~30-50% degradation, smaller warning).

**Consensus-critical refactor — validator ↔ fee_market dedup**

Previously the validator inlined a duplicate `multiplier_x10` table (10/15/20/30) that mirrored `fee_market::congestion_multiplier` (100/150/200/300). Identical thresholds, identical ratios — but two implementations of consensus math is a fork surface the audit firm will flag. Validator now delegates to the canonical `congestion_multiplier`. Bit-identical: `q × (m×10) ÷ 10 == q × (m×100) ÷ 100` for all q where the `checked_mul` chain doesn't overflow. 43/43 consensus tests pass.

**Audit-prep punchlist sweep — ~67 items closed across 4 batches (M+L)**

Headlines beyond the security fix:
• `min_fee_reserve` in churn was ~250× too low (10k atomic units vs the realistic ~3.75M needed for a 2.5KB CLSAG+bulletproof tx) — was silently stalling the churn loop
• `AddressInfo.balance` field removed from RPC types — Article IX privacy compliance (stealth addresses make per-address balances structurally undefined; the struct was dead code anyway)
• `lightwallet.rs` MAX_SCAN_OUTPUTS contract documented + real bug fixed (scanned_to_height was wrong when the cap fired mid-block — callers resuming at `end_height+1` would silently skip blocks)
• `wallet/multisig.rs::reconstruct_group_secret` returns `SecretScalar` (ZeroizeOnDrop) instead of raw `[u8; 32]` — closes the window where the reconstructed key sat on the caller's stack awaiting manual zeroization
• `mempool.rs::unix_now()` monotonic-max via static AtomicU64 — clock hiccup no longer marks fresh entries as 1970
• `chain.rs::calculate_fork_cumulative_work` depth-bounded — CPU-DoS defense on DB prev_hash cycle
• `mining/pool.rs` vardiff decrease path now uses `saturating_mul(7)` (was raw `* 7`, overflow at difficulty > u64::MAX/7)
• `network/bootstrap.rs` signed-manifest 10 MB stat-then-reject — startup-OOM defense
• `network/framing.rs` invalid-magic log dropped from warn → debug (was flooding operator logs on every port scan)
• Plus ~57 verifications closing already-fixed-in-HEAD or N/A-by-design entries

Full ledger: `docs/v1.0-base-chain-hardening-punchlist.md` (~600 lines, every item file:line-tagged for audit-firm review)

**🚨 UPGRADE CHECKLIST — HARD FORK, READ CAREFULLY**
═══════════════════════════════════════════

**This release is a coordinated hard fork.** If you don't upgrade before activation height **{ACTIVATION_HEIGHT_TBD}**, your node will reject the post-fork chain and fall behind. Mining rewards earned on the pre-fork chain after activation will be orphaned.

**Upgrade steps:**

1. **Verify the download:**
   ```
   sha256sum -c SHA256SUMS
   ```
   The published hash matches a clean Docker rebuild from the tagged source.

2. **Stop your node** (and miner if applicable):
   ```
   # Linux/macOS
   pkill -f coincync-node
   pkill -f coincync-rig

   # Windows
   taskkill /IM coincync-node.exe /F
   taskkill /IM coincync-rig.exe /F
   ```

3. **Replace the binary** from the release artifacts. No config changes required, no data migration.

4. **Restart.** Your node will continue syncing on the pre-fork rules and seamlessly transition at the activation height.

5. **Verify upgrade success:** check startup log for `RandomX VM created (mode: full-mem, ...)` if you have ≥3 GB RAM free. If you see `mode: light-jit` or worse, that's expected on smaller systems but you can opt-in to full-mem with sufficient RAM, OR opt-out cleanly with `COINCYNC_RANDOMX_LIGHT_MODE=1`.

**Miners — heads up on first-block-after-upgrade:**

The first hash request per epoch (every 2048 blocks ≈ 2.8 days) triggers a 30-60s dataset build. During that window your miner is at 0 H/s. Subsequent hashes return to full speed. The build runs on whichever thread hits the seed boundary first; other mining threads idle briefly waiting for the dataset, then build their own per-thread VM from it (~ms each). This is one-time per epoch, not per block.

**Wallets — no action required:**

Existing wallets continue to work. The MIN_OUTPUT_AGE rule change is invisible at the UX level — you'll see your fresh coinbase outputs unlock after 100 blocks (~3.3 hours) instead of 10 blocks (~20 min). The wallet displays the correct unlock height; no UI bug.
